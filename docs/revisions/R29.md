# R29 — Otimização Conservadora de Meshes

## Objetivo

A R29 inicia a otimização real do MVP sem sacrificar segurança estrutural.

Ela não tenta simplificar o mapa inteiro de forma automática. Em vez disso, trabalha em dois estágios: primeiro identifica grupos de meshes realmente equivalentes; depois permite relinkar apenas os casos que passam por critérios conservadores de equivalência.

O script principal é:

`tools/blender/r29_optimization.py`

## Pré-requisito

A R29 exige que a R28 já tenha sido aplicada e validada.

Objetos sem `allsaints_r28_class` não são considerados elegíveis para otimização automática.

Se nenhum objeto classificado pela R28 existir, o script aborta em modo fail-closed.

## Modos de execução

### Auditoria — padrão

```bash
blender cena_r28.blend --python tools/blender/r29_optimization.py
```

Neste modo:

- nenhuma referência `obj.data` é alterada;
- grupos de meshes equivalentes são identificados;
- candidatos de LOD são registrados;
- candidatos de colisão simplificada são registrados;
- o mapa é dividido logicamente em células de referência de 128 m para orientar chunks futuros;
- relatórios internos são gravados no `.blend`;
- o resultado é salvo como `_r29.blend`.

### Aplicação exata

Depois que a auditoria for validada:

```bash
blender cena_r28.blend --python tools/blender/r29_optimization.py -- --apply-exact
```

Neste modo, além da auditoria, objetos elegíveis que usam datablocks de mesh comprovadamente equivalentes passam a compartilhar uma mesh canônica.

## Critério de equivalência

A R29 não deduplica objetos apenas porque seus nomes se parecem.

Para serem considerados equivalentes, os meshes precisam coincidir nos dados avaliados pelo fingerprint, incluindo:

- contagem de vértices, arestas, loops e polígonos;
- coordenadas dos vértices;
- topologia das arestas;
- índices de loops;
- material index e smooth state dos polígonos;
- slots e ordem de materiais;
- UV layers e valores de UV;
- atributos suportados e seus valores.

Além disso, ficam automaticamente fora da aplicação exata meshes que apresentem:

- qualquer usuário `HERO` ou `GAMEPLAY`;
- shape keys;
- animation data no mesh;
- fake user;
- custom properties no datablock de mesh;
- atributos cujo tipo ainda não esteja explicitamente suportado pelo fingerprint;
- usuários sem classificação R28.

A filosofia é: se houver dúvida, não otimizar automaticamente.

## O que a R29 pode alterar

Somente no modo `--apply-exact`, objetos elegíveis podem ter sua referência `obj.data` relinkada para uma mesh canônica equivalente.

O script não:

- une objetos;
- executa `Join`;
- aplica `Decimate`;
- triangula meshes;
- altera transforms;
- move objetos entre coleções canônicas;
- apaga explicitamente meshes;
- altera objetos `HERO` ou `GAMEPLAY`.

Meshes duplicadas que ficarem sem usuários podem tornar-se órfãs e deixar de ser persistidas pelo Blender em ciclos normais de salvamento/reabertura, mas a R29 não executa remoção destrutiva explícita desses datablocks.

## Relatórios gerados dentro do Blender

### `R29_OPTIMIZATION_REPORT`

Resumo do modo executado, métricas antes/depois e número de objetos relinkados.

### `R29_EXACT_DUPLICATE_CANDIDATES`

Lista dos grupos detectados, mesh canônica escolhida, usuários, classes e motivos pelos quais outros meshes foram ignorados.

### `R29_LOD_COLLISION_CANDIDATES`

Lista de objetos de maior custo que merecem trabalho posterior de LOD/colisão e estatísticas de células espaciais de 128 m.

## Validação obrigatória no Codex

Antes de aplicar `--apply-exact`, o Codex deve:

1. rodar a R29 em modo de auditoria sobre a R28 validada;
2. abrir o `.blend` gerado;
3. ler os três relatórios internos;
4. confirmar que não houve exceções Python;
5. confirmar que nenhum `HERO` ou `GAMEPLAY` aparece como candidato à deduplicação automática;
6. verificar visualmente alguns grupos de maior impacto;
7. então voltar à R28 validada e executar a R29 com `--apply-exact`;
8. reabrir o arquivo resultante;
9. comparar contagem de objetos e presença dos principais marcos;
10. inspecionar Elevador Lacerda, Praça Cairu, Mercado Modelo e corredor jogável;
11. registrar as métricas reais de redução obtidas.

## Próximo passo

A R30 deve começar o passe visual perceptível do MVP, usando os relatórios de custo da R29 para evitar detalhar áreas que depois precisariam ser reconstruídas.

Prioridades previstas para a R30:

- leitura de ruas e calçadas;
- Praça Cairu;
- entorno imediato do Mercado Modelo;
- conexão visual entre saída inferior do Elevador Lacerda e Cidade Baixa;
- mobiliário urbano modular;
- vegetação controlada;
- iluminação e atmosfera de preview;
- preparação de corredores para tráfego e pedestres;
- pontos de cobertura, atalhos, becos e pequenas rotas alternativas de gameplay.
