# R28 — Gameplay and Export Preparation

## Purpose

R28 moves beyond QA-only helpers and prepares the existing scene for gameplay review, export organization, and measured optimization without destructively reorganizing historical content.

## Changes

### 1. Main gameplay route in Blender

The script creates `32 MVP | GAMEPLAY R28` with three viewport route guides:

- upper entrance to the elevator cabins;
- vertical elevator axis;
- lower exit through Cidade Baixa toward Praça Cairu and Mercado Modelo.

It also creates wireframe gameplay-zone volumes for:

- upper entrance;
- walkway;
- upper cabins;
- lower cabins;
- lower exit;
- Praça Cairu;
- Mercado Modelo.

These helpers are design guides and are excluded from render by default.

### 2. Export classification

The script creates `33 EXPORT | R28` with the following categories:

- `HERO` — priority landmarks and signature architecture;
- `GAMEPLAY` — access points, cabins, doors, circulation, and interaction geometry;
- `TERRAIN` — terrain, slope, cliff, and retaining geometry;
- `ROADS` — streets, avenues, slopes, sidewalks, crossings, and asphalt;
- `DECOR` — benches, railings, trees, signs, street furniture, and similar props;
- `PROXY_OSM` — OSM/reference geometry that should not be exported by default;
- `ENVIRONMENT` — other static environment geometry.

Objects are linked into the export collections without being removed from their original collections. This avoids duplicating mesh datablocks and preserves the historical scene organization.

### 3. Game-ready metadata

Each classified object receives:

- `ordax_r28_class`;
- `ordax_export_default`;
- `ordax_lod_hint`.

`PROXY_OSM` objects receive `ordax_export_default=False` but remain intact and visible.

### 4. Performance audit

The Blender Text Editor receives `R28_PERFORMANCE_AUDIT`, which calculates from the real loaded Blender datablocks:

- object counts by type and R28 class;
- vertex and polygon totals;
- already-shared mesh datablocks;
- repeated object-name groups that may be instancing candidates;
- most-used materials;
- mesh objects with non-uniform scale.

This audit is intentionally generated inside Blender because those relationships should not be guessed from the binary file alone.

## What R28 intentionally does not do

R28 does not:

- delete existing objects;
- mass-rename `.001/.002` objects;
- apply `Join`, `Decimate`, or mass triangulation;
- turn repeated objects into instances based on names alone;
- destructively alter terrain or façades;
- treat route-guide coordinates as certified survey data.

## Validation

After running R28, validate visually that the route and gameplay-zone guides match the intended playable corridor and inspect `R28_PERFORMANCE_AUDIT` before beginning any optimization pass.

## Next step

R29 should use the audit to perform controlled optimization: proven-safe mesh sharing/instancing candidates, collision planning, landmark LOD candidates, road/sidewalk chunk planning, and before/after performance metrics.
